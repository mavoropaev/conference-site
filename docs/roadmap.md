# Возможные направления развития

Список задач, не вошедших в минимальный объём — каждая с обоснованием, тем,
что в коде она затронет, и черновым планом, чтобы при возврате к проекту не
приходилось заново вспоминать контекст. Источник большинства пунктов —
раздел «Известные ограничения» в [README](../README.md#известные-ограничения)
и явные оговорки в [`docs/deploy.md`](deploy.md); здесь — то же самое, но
подробнее и с планом реализации.

Оценка сложности условная: **S** — часы, **M** — день-два, **L** — заметно
больше, отдельная задача сама по себе.

## 1. Восстановление пароля (S)

**Что.** Форма «забыли пароль» — её в проекте сейчас нет вообще: в
`accounts/urls.py` подключены только `signup`, `login`, `logout`.

**Зачем.** Два независимых повода: обычному пользователю, забывшему пароль,
сейчас неоткуда его восстановить; и пользователю, перенесённому командой
`import_legacy`, ставится непригодный для входа пароль (`set_unusable_password`)
— без этой формы войти он не сможет никогда, только если админ вручную
выдаст пароль через `/admin/`.

**Где.** `accounts/urls.py`, `config/settings.py` (нужен `EMAIL_BACKEND`),
новые шаблоны `templates/registration/password_reset_*.html`.

**План.** Django даёт это «из коробки»:
`django.contrib.auth.views.PasswordResetView`,
`PasswordResetDoneView`, `PasswordResetConfirmView`, `PasswordResetCompleteView`
— просто добавить 4 маршрута и 4 простых шаблона (по образцу `login.html`).
В деве `EMAIL_BACKEND = "django.core.mail.backends.console.EmailBackend"`,
письмо видно в логе контейнера. Тест — через `django.core.mail.outbox`.

## 2. Email-уведомления (S–M)

**Что.** Письмо автору при решении по заявке (`submissions.services.decide`)
и рецензенту при назначении (`reviews.services.assign_reviewer`).

**Зачем.** Пункт из исходного технического задания на проект — сейчас
оргкомитет действует молча, участник узнаёт о решении только зайдя на сайт.

**Где.** Не звать `send_mail` прямо из `services.py` — это усложнит тесты
сервисов (пришлось бы мокать email в тестах бизнес-правил). Лучше сигнал
Django (`post_save` на `Submission.status` через `pre_save`+сравнение, или
явный вызов из `services.py` в отдельную функцию `notifications.py`,
которую легко подменить в тестах). Второй вариант проще для чтения кода,
взял бы его.

**План.** `templates/emails/decision.txt` и `assigned.txt` (текстовые —
проще, чем верстать HTML-письма для демо), тест на содержимое
`mail.outbox[0].body`, использует ту же зависимость `EMAIL_BACKEND`, что и
пункт 1.

## 3. E2E-тесты в браузере, Playwright (M)

**Что.** Автоматическая проверка HTMX-сценариев в реальном браузере — сейчас
`tests/test_*.py` проверяют только ответы сервера (Django test client):
заголовки, фрагменты HTML, но не исполнение JS и не визуальный рендер.

**Зачем.** Единственный пробел, отмеченный в обзоре каждого HTMX-слоя при
разработке: `hx-swap-oob` (панель оргкомитета), `hx-push-url` с кнопкой
«Назад» (программа конференции), `hx-confirm` — код ответа проверен, но не
то, что браузер реально это применяет. Ручная проверка в браузере была, но
разово, не в CI.

**Где.** Новый каталог `tests/e2e/`, отдельный маркер pytest
(`@pytest.mark.e2e`), чтобы не гонять в обычном `pytest` — эти тесты
медленнее и требовательнее к окружению.

**План.** `pip install pytest-playwright`, `playwright install chromium`
(нужна сеть — сделать отдельным шагом в `Dockerfile.ci` или в самом
`ci.yml`). Фикстура `live_server` (pytest-django) + `Page` от Playwright.
4 сценария на старт: подача заявки, фильтр программы + кнопка «Назад»,
смена этапа с OOB-обновлением списка, отправка рецензии. Отдельный job в
`ci.yml`, не блокирующий обычные тесты при падении (или блокирующий —
обсудить отдельно).

## 4. i18n / английская версия интерфейса (L)

**Что.** Сейчас все строки интерфейса — русский текст прямо в шаблонах
(`<h1>Мои заявки</h1>`) и в текстах ошибок в `services.py`/`forms.py`, без
единого `{% trans %}` или `_()`. Проверено `grep` по `templates/` и `*.py`
перед тем, как писать этот пункт — раньше в README было неточно написано
«код к этому готов», это исправлено.

**Зачем.** Требование вакансии, под которую делался проект, отдельно
отмечало английский как плюс.

**План.** Не «добавить перевод», а retrofit:
1. Обернуть каждую строку в шаблонах в `{% trans "..." %}` /
   `{% blocktrans %}` (десятки мест — `base.html`, все `templates/*/*.html`).
2. Обернуть тексты ошибок и `verbose_name`/`help_text` в моделях и формах в
   `django.utils.translation.gettext_lazy as _`.
3. `LANGUAGES = [("ru", "Русский"), ("en", "English")]`,
   `LocaleMiddleware` уже подключён.
4. `django-admin makemessages -l en`, перевести `locale/en/LC_MESSAGES/django.po`.
5. Переключатель языка в `base.html` (`{% get_available_languages %}` +
   форма на `django.views.i18n.set_language`).

Самый трудоёмкий пункт списка — если время ограничено, разумнее сделать
частично (только публичные страницы: главная, программа) и явно
задокументировать, что панель оргкомитета и формы остались на русском.

## 5. Экспорт программы конференции (S–M)

**Что.** Кнопка «Скачать программу» на `conferences/program.html`.

**Зачем.** Пункт из исходных расширений: оргкомитету нужно раздать
программу участникам в печатном/переносимом виде, а не только смотреть на
сайте.

**Где.** Новая вьюха в `conferences/views.py`, переиспользует
`submissions.selectors.accepted_submissions`.

**План.** Два формата разумны для старта:
- **CSV** — тривиально, `django.http.HttpResponse` с `csv.writer`, без
  зависимостей.
- **ICS** (календарь) — сложнее осмысленно сделать: у доклада сейчас нет
  времени выступления (только дата конференции целиком), понадобится
  сначала завести `Submission.scheduled_at` или отдельную модель
  «слот в расписании». Без этого ICS-экспорт бессмысленный (все доклады
  «в одно и то же время»).
- PDF — избыточно для демо-проекта, нужна ещё одна зависимость (`weasyprint`
  или подобная) ради малой пользы.

Начать с CSV, ICS отложить до появления модели расписания.

## 6. Дедлайны по датам, автоматический переход этапов (M)

**Что.** Сейчас `Conference.advance()`/`revert()` вызываются только вручную
(оргкомитетом) — так решили сознательно на этапе проектирования моделей,
чтобы не усложнять первую версию.

**Зачем.** Реалистичнее: «приём заявок до 1 ноября» сам закрывается в срок,
а не когда кто-то из оргкомитета вспомнит нажать кнопку.

**Где.** `Conference` — добавить необязательные поля-дедлайны
(`submission_deadline`, `review_deadline`, ...), management-команда
`advance_due_conferences` (аналог `seed_demo`) на `cron`/Celery beat.

**План.** Дедлайн — не замена ручному переходу, а его инициатор: та же
`advance()`, тот же журнал `StageTransition`, только `changed_by=None` и
`reason="автоматически по дедлайну"`. Нужно решить: `PermissionDenied`
внутри `advance()` сейчас требует `by.has_perm(...)` — для автоматического
вызова понадобится либо системный пользователь, либо отдельный
метод-обход прав специально для планировщика (второе чище).

## 7. Гибкость CSV-импорта (S)

**Что.** `import_legacy` понимает только UTF-8 (точнее, `utf-8-sig` —
терпит BOM от Excel) и запятую как разделитель (`csv.DictReader` без
параметров).

**Зачем.** Реальная выгрузка из Drupal может оказаться в CP1251 или с `;`
(особенно у старых российских инсталляций).

**Где.** `legacy_import/management/commands/import_legacy.py`, функция
`_read_rows`.

**План.** Аргументы командной строки `--encoding` (по умолчанию
`utf-8-sig`) и `--delimiter` (по умолчанию `,`), проброс в `open()` и
`csv.DictReader(handle, delimiter=...)`. Тесты — тот же файл, что уже есть
(`tests/test_import_legacy_command.py`), плюс один тест с CP1251 и `;`.

## 8. Полнотекстовый поиск в программе (S–M)

**Что.** `submissions/selectors.py:search_program` ищет через `icontains`
(`Q(title__icontains=query) | ...`) — линейный просмотр без индекса,
работает, но не масштабируется.

**Зачем.** Для текущего объёма (десятки докладов на конференцию) это
сознательный, а не случайный выбор — `icontains` проще, не требует лишней
инфраструктуры. Стоит доработки только если конференции в системе станут
крупными (сотни-тысячи докладов).

**Где.** Тот же `selectors.py`.

**План.** PostgreSQL умеет это нативно, без внешних сервисов:
`SearchVector`/`SearchQuery` (`django.contrib.postgres.search`) с
`GinIndex` на `Submission`, либо `pg_trgm` для опечаток. Не браться раньше,
чем появится реальная причина — преждевременная оптимизация.

## 9. Деплой без простоя (L, низкий приоритет)

**Что.** `docs/deploy.md` сейчас честно говорит: `systemctl restart` даёт
короткий простой при каждом обновлении кода.

**Зачем.** Не критично для конференции с несколькими релизами в год, но
если проект вырастет — заметно.

**План.** Второй набор gunicorn-воркеров на другом сокете + переключение
`proxy_pass` в nginx (или `systemd` socket activation с двумя instance),
переключение после успешного health-check нового набора. Отдельная
задача, не имеет смысла делать раньше остальных пунктов этого списка.

## 10. Проверка содержимого загружаемых файлов (S–M)

**Что.** `submissions/models.py`: `FileExtensionValidator(["pdf", "doc", "docx"])`
проверяет только расширение имени файла, не содержимое.

**Зачем.** Расширение легко подделать; для реального сайта, принимающего
файлы от посторонних, разумна проверка сигнатуры файла (magic bytes) и/или
антивирусное сканирование.

**Где.** `submissions/models.py:validate_file_size` — рядом добавить
`validate_file_content`.

**План.** Минимум — библиотека `python-magic` (проверка реального
MIME-типа по содержимому, не по расширению). Полноценное антивирусное
сканирование (ClamAV) — отдельная инфраструктурная задача, есть смысл
только при реальном продакшене с недоверенными загрузками.
