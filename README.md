# Сайт научной конференции

Сайт для сопровождения научных конференций — приём заявок на доклады,
рецензирование, регистрация участников, публичная программа и панель
оргкомитета.

Предметная область и данные полностью выдуманы, проект не связан с каким-
либо рабочим кодом или реальной конференцией.

## Идея

Небольшие ежегодные научные конференции часто держатся на связке
Google-форм, почты и постаревшего сайта на Drupal — без единой истории
участников и без прозрачности, кто и когда принял решение по заявке.
Тяжёлые платные платформы вроде EasyChair или ConfTool для такого
масштаба избыточны: недёшево, данные участников — на чужой стороне,
доработать под себя нельзя. Прототип рассчитан именно на этот сценарий:
прозрачные этапы с журналом решений, свой self-hosted стек и перенос
истории участников со старого сайта без потерь.

## Стек

Python 3.12, Django 5.2 (LTS), PostgreSQL 16, HTMX 2.0.4, чистый SCSS
(`django-sass-processor`, без Tailwind/Bootstrap), pytest + pytest-django,
ruff, Docker Compose, GitHub Actions.

## Как запустить

```bash
cp .env.example .env      # заполнить POSTGRES_PASSWORD и DJANGO_SECRET_KEY
docker compose up
```

Сайт откроется на <http://localhost:8000>. Миграции применяются автоматически
при старте контейнера `web` (см. `command` в `docker-compose.yml`).

Демо-данные для ручной проверки (вымышленные конференции, пользователи всех
ролей, доклады):

```bash
docker compose exec web python manage.py seed_demo
```

Команда идемпотентна — повторный запуск не создаёт дублей. Пароль у всех
демо-пользователей: `demo-pass-123`. Роли:

- `organizer@example.com` — оргкомитет (панель `/organizer/`, вход в админку)
- `reviewer1@example.com`, `reviewer2@example.com` — рецензенты
- `author1@example.com`, `author2@example.com`, `author3@example.com` — участники

### Тесты и линтер

```bash
docker compose run --rm web pytest
docker compose run --rm web ruff check .
docker compose run --rm web ruff format --check .
```

### Перенос данных из старой системы

```bash
docker compose exec web python manage.py import_legacy \
    legacy_data/users.csv legacy_data/participations.csv --dry-run
```

Без `--dry-run` изменения сохраняются. Пример CSV с вымышленными данными —
в `legacy_data/`. Подробности в разделе «Перенос данных» ниже.

## Архитектура

Django-проект `config/`, приложения по предметным областям:

```
accounts/       — кастомный User (вход по email), Profile, роли (группы)
conferences/    — Conference, этапы, журнал переходов; management-команда seed_demo
submissions/    — заявки на доклады (Submission), регистрации (Registration)
reviews/        — рецензии (Review)
organizer/      — панель оргкомитета (только вьюхи и шаблоны, без моделей)
legacy_import/  — перенос данных из CSV (import_legacy)
```

Внутри каждого приложения с бизнес-правилами — три слоя:

- **`models.py`** — данные и ограничения на уровне БД (constraints, индексы).
- **`services.py`** — правила и переходы состояний (кто, когда, при каком
  этапе может что-то сделать); бросают `SubmissionError`/`ReviewError`/
  `PermissionDenied` с текстом для пользователя.
- **`selectors.py`** (где есть) — выборки только для чтения, отдельно от
  правил изменения.
- **`views.py`** — тонкие: разбирают запрос, вызывают сервис, решают, отдать
  ли фрагмент HTMX или полную страницу.

Такое разделение позволяет тестировать бизнес-правила без HTTP (см.
`tests/test_*_services.py`) и держать вьюхи короткими.

### HTMX без отдельного фронтенд-стека

Каждый интерактивный адрес отдаёт HTML-фрагмент при заголовке `HX-Request`
и полную страницу иначе — интерфейс работает и с выключенным JavaScript.
Примеры паттернов:

- `hx-push-url` — фильтр программы конференции меняет адрес страницы, работает
  кнопка «Назад» (обрабатывается отдельно через `HX-History-Restore-Request`).
- `hx-swap-oob` — смена этапа конференции одним ответом обновляет и блок
  этапа, и список заявок (у него меняются доступные действия).
- `hx-confirm` — подтверждение перед необратимыми действиями (переход этапа).

## Схема данных

```
User (accounts) 1───1 Profile ──┬──< Submission >── Conference
                                  │        │
                                  │        └──< Review >── User (reviewer)
                                  └──< Registration >── Conference
```

- `Profile.legacy_id` — естественный ключ для идемпотентного переноса из
  старой системы.
- `Conference.stage` — управляет тем, что доступно на сайте (приём заявок,
  рецензирование и т.д.); переходы фиксируются в `StageTransition`.
- `UniqueConstraint(Submission, reviewer)` — один рецензент, одна рецензия на
  доклад. `UniqueConstraint(Registration: conference, participant)` — одна
  регистрация на конференцию.
- `CheckConstraint` — оценка рецензии от 1 до 5, дата окончания конференции
  не раньше даты начала.

Полные определения — в `*/models.py`, миграции — в `*/migrations/`.

## Роли и права

Три роли (группы Django), права описаны в коде (`accounts/roles.py`) и
приводятся к нему при каждом `migrate`:

- **Участник** — подаёт заявки на открытых этапах, видит свои заявки.
- **Рецензент** — видит назначенные ему заявки (без автора — слепое
  рецензирование), ставит оценку 1–5 и комментарий.
- **Оргкомитет** — управляет этапами, назначает рецензентов, принимает
  решения по заявкам.

## Design decisions

**Кастомная модель `User` с самого начала.** Django не позволяет безболезненно
заменить `User` после первой миграции, поэтому вход по email сделан в первой
же миграции проекта, хотя `username` в демо не нужен был бы вовсе.

**Машина этапов вместо статус-флагов.** `Conference.advance()`/`revert()`
переводят конференцию по строго заданной последовательности этапов,
проверяют право и (для возврата) требуют причину; каждый переход пишется в
`StageTransition`. Прямая правка поля `stage` закрыта даже в админке —
иначе терялась бы история и не проверялись бы права.

**Сервисный слой, а не «толстые» вьюхи или сигналы.** Правила вроде «заявку
можно редактировать только на этапе приёма» или «автор не рецензирует
собственный доклад» живут в `services.py` и тестируются без HTTP. Вьюхи
только переводят HTTP-запрос в вызов сервиса и выбирают, что вернуть.

**Слепое рецензирование.** Выборки для рецензента (`reviews/views.py`)
никогда не подгружают автора заявки — не потому что шаблон его не выводит,
а потому что данных об авторе в контексте вообще нет.

**Идемпотентный перенос по `legacy_id`, а не по имени.** Имена и email при
миграции с Drupal могут меняться или совпадать; `Profile.legacy_id` —
единственный надёжный естественный ключ. Если человек уже
зарегистрировался на новом сайте сам, импорт находит его по email и
привязывает историю, а не создаёт дубль.

**HTMX, а не SPA-фреймворк.** Подход «HTML с сервера, точечно
оживлённый», а не отдельный JS-фронтенд — проще в сопровождении и не
требует отдельной сборки.

## Известные ограничения

Список того, что сознательно не сделано или не проверено — честно, а не
скрыто:

- HTMX-фрагменты проверены через ответы сервера (pytest), не в реальном
  браузере автоматическими тестами; ручная проверка в браузере пройдена
  (см. историю разработки), но без Playwright/Selenium в CI.
- Нет email-уведомлений о смене статуса заявки.
- Реализована только «половина» слепой рецензии: рецензент не видит автора
  заявки. Автору при этом вообще не показываются рецензии и рецензенты — не
  как осознанная анонимность, а потому что такого экрана в демо нет.
- `import_legacy` ожидает CSV в UTF-8 с запятой как разделителем; другие
  кодировки/разделители не поддерживаются.
- Нет i18n: строки зашиты на русском прямо в шаблонах и в текстах ошибок
  в `services.py`/`forms.py`, без `{% trans %}`/`gettext`. Добавление
  английской версии — не «доперевести», а переписать каждую строку
  интерфейса заново.
- Файлы заявок не проверяются антивирусом и не сканируются на содержимое,
  только по расширению и размеру.
- Нет формы «забыли пароль»: импортированный из старой системы пользователь
  получает непригодный для входа пароль и не может войти сам, пока
  администратор не выдаст ему новый через админку.

Все пункты выше — кандидаты в [`docs/roadmap.md`](docs/roadmap.md), там
подробнее о том, что и как можно доделать.

```
226 тестов, pytest + pytest-django
```

Покрывают: модели и ограничения БД, переходы между этапами и права,
HTMX-вьюхи (фрагмент vs. полная страница), число SQL-запросов (защита от
N+1 на страницах со списками), идемпотентность импорта.
